# Blockbench fork: custom tools for Distant Early Warning

Personal fork of Blockbench (JannisX11/blockbench), on upstream 5.2.0 since the 2026-09-20 port (5.1.6 before that). All work goes on branch `custom`. `master` just mirrors upstream. The fork took no upstream updates between 2026-09-11 and the 5.2 port, which the user asked for to keep upstream's new features; core files may still be changed freely. How an upstream release gets taken in: `git merge master` into a side branch in its own worktree (own `node_modules` and `dist-electron`, so the package the user works with stays intact), resolve, then `python tests/dew/audit_fork_lines.py` to check that every line the fork added to a core file still exists somewhere in the merged tree (upstream moves code between files, and a fork change to moved code lands in a conflict or is lost; the 5.2 port found all of them in conflicts), then the whole dew suite against a baseline run of the same suite on the old tree.

## Roadmap (user, 2026-09-15)
The fork is permanent and refined for the long run (upstream updates were off the table when this was written; the 5.2 port of 2026-09-20 changed that, see above). Three tracks, in this order: (1) performance for mid-poly meshes, 1 to 10k faces (done 2026-09-15/16 to the user's satisfaction: drags, undo, selection, UV panel; `probe_perf.mjs` and `probe_hitch.mjs` in the scratchpad pattern are the yardsticks: measure on the real file with the real keymap, fix one thing, re-measure); (2) importing models with a rig, and (3) textures up to 2048 x 2048, both now the current track: stabilise the import path first. Decided 2026-09-16 (user): the fork is the one-stop tool for anything low or mid poly; complex characters are bought or downloaded rigged (usually made in Blender, which is installed at `D:/Blender 5.2/blender.exe` and converts headless in under a second), imported as glTF, posed in the Animate tab, and the poses go to the game as a pose file keyed by bone name while the mesh stays the glTF it came as (Godot imports that natively). Re-exporting a mesh from the fork is the second step, only when a bought mesh gets edited here. An FBX or .blend converter through headless Blender is deferred until a model arrives without a glTF. Performance rule learned: a static probe misses costs that only appear while a selection is changing; replay the user's exact gesture on his file.

## Commands
- `npm run build-electron`: bundle, about half a second. After every change.
- `npm run dev`: dev app with remote debugging on port 9223 (since 5.2 upstream's own launcher, `build.js --watch --launch`, which keeps the port).
- `npm run app`: packaged app in `dist-electron/win-unpacked`, plus `Blockbench.lnk` in the repo root. Fails while Blockbench is open (exe locked), so check `tasklist | grep -i blockbench` first and skip or ask.
- `node tests/dew/run_cdp.mjs tests/dew/<test>.mjs --isolated`: one scripted test over CDP. It reuses the dev app that is already up and leaves it running, so working on a test does not reopen a window every run (about 10 s the first time, 3 to 4 s after). `--isolated` uses a separate profile; required whenever the packaged app is open, and a shared app is restarted when a run asks for the other profile.
- `npm run test:dew:stop`: close the shared dev app.
- `npm run test:dew`: every test in sequence, each in its own app (`--fresh`), which also closes a shared one. Requested milestones only.
- `node tests/dew/run_cdp.mjs tests/dew/probe_keymap.mjs`: the user's live keymap, sub-keybinds included (run without `--isolated` so it reads his profile).

## Working rules
- Commit each verified change on `custom` without asking; never push (the user pushes from GitHub Desktop).
- Per change: build, run the test for the feature touched (not the whole suite), then `npm run app` and close the dev app (`npm run test:dew:stop`). Speed matters more than exhaustive testing right now.
- The package is what the user tests, so it must never be behind the code: a build 39 minutes old once produced a bug report for something already fixed, and the screenshots matched the old behaviour exactly. If `npm run app` is skipped because Blockbench is open, say so in the reply rather than letting it pass quietly.
- Simple heuristics over optimal ones. Every tunable is a named constant: `BRUSH` in `js/dew/tile_brush.js`, `DEW` in `js/dew/dew_scene.js`.
- No em dashes anywhere (code, comments, commits, replies). Use Bash, not PowerShell.
- The user builds all game content (rooms, clusters). Claude builds and tests tools only.

- Inverse kinematics on imported rigs (core `js/animations/fabrik.ts` and `displayIK` in `js/animations/timeline_animators.js`, 2026-09-21). Stock 5.2 IK: a Null Object with IK Target (the bone whose HEAD is pulled, the palm or foot), IK Root (the top of the chain, upper arm or thigh; the chain is every bone between by outliner parenthood, root included) and an optional IK Pole (a Group, Locator or Null Object the middle joint bends toward; nothing happens on a two-node chain), plus Lock IK Target Rotation (the target keeps its world rotation). The target picker lists nodes at least one level under the null object's own parent list, so a handle at ROOT level sees every bone of an armature beside it. IK runs in EVERY animation once a handle has a target (`getBoneAnimator` creates the animator on demand and `displayIK` checks no keyframes), so any preset that moves a wrist or ankle off rest needs a position key on the handle putting it there, or the limb is pulled back to rest; Export Poses reads the solved pose since it stacks the animation; Animation > Bake Inverse Kinematics writes the solved rotations as bone keys. - `js/dew/dew_mirror.js`: Live Mirror (2026-09-21), the user's replacement for stock Mirror Modeling, which repeats every edit on a real second half while it is on (slow, and it edits what was not asked for). This one only DRAWS the selected mesh or cube again, flipped across its OWN axis through its pivot (local space; the world axis for anything unrotated). The preview is a `THREE.Mesh` child of the element's scene object sharing the element's OWN `geometry` and `material` objects with a scale of -1 on the axis, so it follows every drag, edit and posed deformation with no copying at all (three flips the winding itself for a negative determinant, and the face shaders light from `modelMatrix * normal`, so the mirrored half is lit correctly); it is named `dew_mirror`, carries `no_export` (the glTF exporter skips it) and an empty `raycast`, and is in no pick list, so it cannot be clicked. `syncPreviews` runs from a chained `Canvas.scene.onBeforeRender` (installed on first use, the scene is null at module load): it makes missing previews, re-links geometry or material when a rebuild replaced them, and removes previews whose element lost its mirror, was rebuilt on a new scene object, or belongs to a project that is not open. - `js/dew/tile_brush.js`: Tile Select, Tile Brush, Shave, Ramp, Texture Brush, Paint Bucket and their shared helpers (`describeTile`, `tileUV`, `blockTiles`, `atlasRegion`, `originCell`, `footprintCell`, `buildTileIndex`, `hitFace`, snapshot raycast for erasing). Two cells meet along the edge under the cursor, and the brush takes the one that closes a gap: `edgePoint` scores both sides with `fillScore`, where a cell already filled scores -1 and an empty one counts the tiles it would sit against in the same plane, and a tie keeps the far side, which is what still lands a wall started on a floor above it rather than under it. Only a face standing across the work plane offers a choice at all. Tab (`dew_tile_edge_side`) flips to the other side and resets when the brush is picked up. It shares its key with the ramp's own Tab action, and both declare `condition: {tools: [...]}` because `Condition.mutuallyExclusive` only reads object conditions, so a function condition there would have them flagged as conflicting in the keybind settings (`cdp_edge_side.mjs` checks both). Shave cuts outside corners at 45 degrees one block deep (16 or 32 per C, full size only on the 32 grid), keeps the touched side's texture, and closes the ends (trims end-plane tiles, adds or removes notch triangles). Ramp draws 45 degree faces from an edge: a piece started on a flat tile folds away from it (out across the edge, then out of the plane), one started on a diagonal continues that diagonal, and dragging adds further pieces in a straight line (`rampReach` counts them from the closest approach of the cursor ray to the run line). Starting on an inside corner still fills it as before, through `shaveTarget` / `shaveCorner` with the `inside` flag, and the run carries on from that slope's top edge. `run.min_pieces` is what a plain click places: 0 after a corner fill, 1 for a free diagonal. Free diagonals add no end triangles and delete nothing; only the corner case clears the tiles behind the slope. `shaveTarget` tries the hovered block's edges nearest first and takes the nearest one that carries a corner, so a hover anywhere on the tile works. End triangles cancel against a neighbouring cut of the same size, and nest by size otherwise (a smaller one is removed, a larger one already covers the end). After a stroke `capTriangularHoles` fills three-edge holes bordered by that stroke's faces: the gap left where a ramp meets flat tiles, or where two cuts meet. It matches edges by position, so a ramp in one element closes against a wall in another, and it runs after tile-brush painting too, so a wall painted beside a ramp closes itself. The search starts at an open edge of the stroke, but any edge can close the loop, open or not: a floor that carries on underneath a ramp shares that edge with the next floor tile, and requiring all three edges to be open used to leave exactly that gap open (`cdp_ramp_floor.mjs`). Whether a loop is really a hole is settled by the area and coverage tests, not by edge counts. Two things are not holes and are skipped: collinear loops (T-junctions between a long edge and two short ones) and loops a coplanar face already fills (a square wall tile closing the end of a wedge). The second test is the area the candidate shares with that face (`faceOverlaps`, Sutherland-Hodgman clipping, threshold `BRUSH.OVERLAP_AREA`), not whether its centre is covered: a face filling only part of a candidate leaves the centre clear, so a cap went on top of it and z-fought. The tests use the same two rules when counting holes. Neither tool responds on the back of a wall (no face there, so no corner) or at full size against a corner that is not on the 32 grid. The texture brush and the bucket also paint what is not a tile: a ramp diagonal or a cap triangle takes a cell through `faceFrame`, which builds a frame from the face's own normal (down follows gravity across the face, flat faces read like a floor, matching `tileUV`) and stretches the cell over the face's box, so a ramp reads like the tiles around it only longer. Atlas picks are counted in half cells whatever C says (`atlasRegion`). The texture brush lays the pick over its own footprint from the upper left as the texture reads (`footprintCell`): a pick smaller than the footprint repeats, so a full size brush with one cell paints all four tiles with it, and a larger one keeps its upper left cells. The fills (bucket, tile brush, Whole Block, all three sharing the pick) tile it from the plane origin instead (`originCell`), so separate strokes and blocks line up. A loose face has no grid to run along, so it takes the upper left of the pick, as much as the brush size holds and the hover lights the face itself rather than a cell. An atlas cell clicked again walks square, upper left half, lower right half (`ATLAS_SHAPES`, drawn on the overlay with a clip path); dragging past the cell goes back to squares. A triangle takes the half that is picked, turned 180 degrees about the cell centre when that is not the half it already lands on, which swaps halves without mirroring the art, so two triangles can share one cell. Quads always take the whole square. Ctrl with the Ramp tool erases instead of drawing: click or drag over a diagonal or a triangle to delete it (a red on-top ghost marks what will go), while flat tiles are left to the tile brush, so a mis-drawn slope comes off without undoing the whole run. It uses the same stroke-start snapshot raycast as the other erasers. Alt is the eyedropper on three tools: on the tile brush `pickTilePlane` takes the plane and the facing of the tile under the cursor, on the texture brush and the bucket `pickAtlasFromTile` takes the atlas cell that tile was painted with, reading it off the lowest uv corner of the face and selecting that texture. A picked facing lives in `state.sign`, where null means follow the camera as before, so tiles keep facing the way they were picked even after orbiting to the other side (where back-face culling then hides them, which is the point of Tab and W); W turns the plane and clears it. The plane grid's own lift still uses `facingSign`, since that is about drawing toward the viewer (`cdp_eyedropper.mjs`). Two costs are held down here (`cdp_paint_perf.mjs`): `buildOccupancy` and `buildTileIndex` are cached in `scan_cache` until `finished_edit`, `undo`, `redo` or `select_project`, since the hover path ran a whole-scene scan on every mouse move, and paint and erase steps call `scheduleRebuild` instead of `Canvas.updateView`, which collapses a drag crossing several tiles into one rebuild per frame (`cancelRebuild` in `endStroke` drops the frame the stroke's own final update covers). Anything mutating a scan must copy it first, as `startStroke` does; `shaveStep` rebuilds its index mid-stroke and so keeps calling `buildTileIndex` directly, while hovers use `hoverTileIndex`.
- Whole Block (`dew_whole_block`, between Tile Select and Tile Brush): drops a cube of half cell tiles into the cell under the cursor, on the near side of whatever it points at, falling back to the work plane over open space. C sizes it, W / A / D aim the plane, and a drag keeps the plane it started on so it lays a run rather than climbing what it just placed. It is an `atlas_picker` tool like the texture brush and shares its pick (`texture_state.atlas`): with a pick, every side a stroke adds is painted through `paintBlockSide`, which tiles a multi-cell pick from the plane origin the way the bucket does, so a row of blocks alternates cells unbroken; without one, sides stay untextured. Alt picks up a tile's cell (`pickAtlasFromTile`). A wall put back by Ctrl stays untextured. Culling only ever happens within one element: another element's face is left alone and the block adds its own side (unless the two would face the same way and z-fight), so separate objects stay whole when moved apart, and Cull Overlapping Faces remains the deliberate merge. Add DEW Block (`dew_add_block`, first in the outliner's + menu so the + button itself runs it in DEW scenes, and in the Mesh menu) starts a new element named `block` holding one block at the camera's orbit point snapped to the brush size, selected, so the tile tools build into it (`cdp_add_block.mjs`). Within an element: a side landing where a face already stands is skipped. That face goes too when it is the wall of a block on the other side, since it sits between two solids and back-face culling showed it from inside the neighbour; anything else (a floor, a lone wall) stays. Ctrl removes only what faces out of the cell, and gives a neighbouring block back the wall they shared. Both hinge on `blockOwner`: a cell counts as a block when faces point out of it on at least `BRUSH.BLOCK_SIDES` (2) sides besides the shared one. One side is not enough, because a floor tile is exactly the top of an empty cell under it, and taking that for a block hung walls under the ground (the old seal's bug, and test M). Known misjudgements: a hollow building made of outward-facing tiles looks like a block at its corners, so a block pushed against one there opens that wall; a block buried on all but one side looks empty, so its shared wall stays. - Terrain Brush (`dew_terrain`, after Ramp in the toolbar, no key yet): raises the tile under the cursor a step (`BRUSH.TERRAIN_STEP`, 16, so 45 degrees), Ctrl lowers, Shift flattens (every cell a drag touches goes to the height under the cursor where the stroke started, snapped to a step, up or down; `settleTerrain` with dir 0, whose spread clamps neighbours both ways), C sizes it, a drag raises each cell once measured against the ground as the stroke found it, so it lays an even ridge. ## Traps
- A tool's KEY ignores the tool's CONDITION when nothing else took the key: the keydown handler in `js/interface/keyboard.js` ends with a fallback that walks `Tool.all` and calls `switchModeAndSelect` on the first tool bound to the key, which selects the first available mode in the tool's `modes` list and then the tool, never asking its condition (stock, there so that B in Edit jumps to Paint and picks the brush). That is how pressing 2 in a generic model picked Whole Block (reported by the user 2026-09-20): with a mesh selected the key went to the selection mode, with nothing selected it fell through to the fallback. A tool opts out with `switch_mode_by_key: false` (all nine Block Painting tools: their keys work in the tab only and never pull the user into it), and `switchModeAndSelect` now also refuses a tool whose condition still fails after the switch. A probe that reads `Condition(tool.condition)` will say the key is safe when it is not: press the real key.
- An upstream merge can break the fork with NO conflict and NO build error: 5.2 moved the selection rectangle handlers from `preview.sr_move_f` to `preview.selection.sr_move_f`, and the fork's readers of the old place (parking the orbit controls for the Shift box select, the UV panel deferral in `uv.js`) simply saw `undefined`, so the Shift drag zoomed the camera. Only the suite diff against a baseline run caught it. After a merge, list the members upstream removed from a class the fork reads (`git show <ref>:<file> | grep -oE "this\.[a-z_]+" | sort -u` on both sides, `comm -23`) and grep the fork for each.
- A dev app reused between test runs keeps the bundle it started with, so the runner starts it again when `dist/bundle.js` is newer than `performance.timeOrigin` of the page. Reloading instead of restarting looks cheaper and is a trap: `Page.reload` takes Blockbench down with it, and waiting for `Blockbench` to be defined passes immediately on the page that is still up, so the test runs against the old bundle and lies. Three chased bugs today were stale code. A reused app also carries its view over, and a test that drags across the screen picks up whatever the path crosses, so the reset puts the camera back to a fixed place. `--fresh` (what the suite uses) has neither problem and is the one to trust when a drag test disagrees with itself.
- Face mode selection with Shift (`js/preview/preview.ts`, `startPaintSelect`): a Shift + left press on a mesh face starts the fork's paint select (every face the cursor passes over is added); the same press over nothing starts the stock selection rectangle (`startSelRect`), whose shift handling adds the faces the rectangle touches to the old selection. Two traps met on the way: the default keymap makes Shift + left drag over nothing the camera zoom (`preview_zoom` is key 1 with shift), and the orbit controls only stand down when the pointer is over geometry, so the rectangle path parks `controls.enabled` until mouseup; and the stock `canvas_unselect` mouseup cleared the face selection after any shift click that hit nothing, which is now skipped while shift is held. The stock rectangle counts a face as inside when any edge touches the rectangle, so a box selects the faces it clips as well as the ones it contains (`cdp_area_select_faces.mjs`). A reported hitch while drag-selecting faces was measured against the pre-performance code and was not a regression (identical at 2k faces, worse before at 10k); it was the UV panel redrawing every selected face, with its four vertex handles each, on every mouse move of a growing selection, plus the stock rectangle appending vertices and faces with `safePush` and `includes`, quadratic in the selection. Fixed in two places: the UV panel draws no faces while a rectangle or a paint select is in progress and redraws on release (`UVEditor.defer_during_area_select`; `getDisplayedUVElements` reads `Preview.selected.sr_move_f` and `paint_move_f`, which are outside Vue reactivity, so `stopSelRect` and `stopPaintSelect` call `$forceUpdate`), and `viewportRectangleOverlap` dedupes through Sets. Worst frame during a box over 1225 faces: 158 ms to 38. The user's own confirmation: with the UV panel folded the drag was instant, open it slowed progressively. Second round, on the real revolver (4223 faces, the user's keymap has the area select on plain Left Click): the drawing deferral was not enough, since `UVEditor.loadData` still ran on every move from the global selection update and its `displayTools` slider refresh recomputed uv extents over every selected face, 170 ms a move (3.7 s over one drag, zero in a steady state, which is why a static probe missed it). `loadData` now returns early while a rectangle or paint select is in progress and the release handlers call it once. What remains per move at that size: the transform gizmo placement (`Transformer.updateSelection` via `center()`, about 18 ms), the colour pass and the rectangle test, all flat, none growing.
- Anything sized or placed with `camera.fov` breaks in an orthographic view, which has no fov (NaN). Hit so far: locator icons (the fork's arrow sizes from the projection matrix, safe), the old Fit View on Open (removed 2026-09-25, it blanked ortho files on open), and null objects (IK handles and poles vanished in ortho; fixed 2026-09-25 in `null_object.js` `updateWindowSize`: the size comes from the rendering camera's `projectionMatrix.elements[5]`, keeping stock's exact perspective size (0.38 * fov / height) and the same pixels in ortho at any zoom, refreshed per camera by a chained render hook like the locator's; `cdp_null_ortho.mjs`, 5 checks, 276 px in both modes and a real click in ortho). Grep for `.fov` before trusting new view code in ortho.
- Right-clicking in the preview reaches an element's own menu only when `Toolbox.selected.selectElements` is truthy, and every DEW tool sets it false. A tool that wants a context menu opens one itself from `onCanvasRightClick` and returns false, which stops the preview's camera menu opening as well.
- Settings live in the profile and survive a kill, so a format must never write one: whatever puts it back is skipped by a crash or a force-quit, and the value then applies to every other project. `dew_scene` had this with `edit_size`, which left generic models snapping by half cells, and now declares `Format.edit_size` for `canvasGridSize` to read instead. Anything else a format needs to change about the app belongs in the format, not in settings.
- An Electron window behind another window counts as occluded and stops producing frames: `Page.captureScreenshot` then waits a minute or more, and `requestAnimationFrame` may never fire. The runner launches with `--disable-backgrounding-occluded-windows --disable-renderer-backgrounding --disable-background-timer-throttling`. Without them a reused app took 105 s for a test that takes 4. Never wait on rAF from a test for the same reason: render through `Preview.render()` instead.
- Performance, measured on a 3600 to 6400 tile mesh: a `Canvas.updateView` with `geometry: true` rebuilds that whole element, around 13 microseconds per face, so anything per-tile has to be batched. A whole-scene face scan is around 5 microseconds per face, which is why hover paths cache. Selection lookups used to be arrays scanned once per face (`selected_faces.indexOf(fkey)` in `updateHighlight`, the same shape for vertices and edges in `updateSelection`), quadratic in a big mesh, now Sets. Rendering itself is not the problem: 6400 tiles with everything selected still draws at 140 fps.
- The UV editor draws about 7 DOM nodes per face of every element it displays, so highlighting a few thousand tiles in face mode makes `updateSelection` take about 600 ms (44,000 nodes at 6400 faces). Object mode is cheap (88 nodes), and `getDisplayedUVElements` already returns `[]` for `atlas_picker` tools, which is where a cap would go. Not capped yet: it hides UV faces, which is the user's call (`probe_uv_cost.mjs` has the numbers).
- `cdp_cage_smooth.mjs` has a PRE-EXISTING intermittent failure in 'switching to Move preserves the existing curve and uses linear movement': measured 2026-09-20 at 4 of 8 `--fresh` runs on the code before that day's toolbar work and 1 of 8 after, so it is older than that work and not caused by it. Always the same check, never another. Lead, not yet chased: it is the only geometry-asserting check that passes `{clientX, clientY}` to `DEWCage.begin` WITHOUT `pointerId`, where `scaleCage` and cdp_cage's `beginTest` both pass `pointerId: 1`. The two other checks that omit it only assert that nothing changed, so they would pass even if the drag never started. Do not read one green run of this file as proof; run it several times.
- Blockbench overwrites `Object3D.type` on element meshes with its own name (`'cube'`, `'mesh'`), so a three.js style `object.type == 'Mesh'` test matches NOTHING and any raycast built on it comes back empty. Use `object.isMesh`, which stays on the prototype.
- `--color-axis-x/y/z` (and `-u/v/w`) are declared TWICE with different values: the UI palette globally (`css/setup.css`, x is `#ff1242`) and the 3D palette on `#preview` (`css/window.css`, x is `#fd3043`), and it is the `#preview` one that themes.ts copies into `Canvas.gizmo_colors`. So the stock `.color_x` class, or any `var(--color-axis-x)` outside the preview, gives a colour that does NOT match the gizmo handle it names. Anything meant to read against the 3D view must resolve the variable on `#preview` (`getComputedStyle(document.getElementById('preview'))`). Same shape as the `--color-ground` trap: these variables are scoped, and a theme can move the two apart further.
- Blockbench saves the WHOLE keymap to localStorage (`keybindings`, 669 entries on the user's profile, 100 with a key), not just the bindings a user changed, and `actions.ts` lets a stored entry override the source default at construction. So changing a `keybind:` default in source is INERT on any existing profile. Moving a key needs a guarded one-time migration against the live keybind objects (`keybind.clear()`, `keybind.set({key}).save()`), run after every module's `defineActions` (a `setTimeout(..., 0)` is enough), flagged in localStorage so a later rebind by the user is not taken back. `migrateCageKeybind` in `js/dew/dew_cage.js` is the worked example; it only reclaims the key while the old owner still holds the stock bare binding.
- Keymap labels: a bracketed modifier ("[Ctrl] + [Shift] + Page Up") is optional, so the bare key is taken. Sub-keybinds (selection modes, slider nudges) are separate from action keybinds; check both before proposing keys.
